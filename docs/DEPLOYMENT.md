# Deployment Record — Isolated WSL2 + FrankenPHP LAN Server

Authoritative record of the current deployment: how the VMS is installed, exposed on the LAN, what was changed, the bugs fixed to get here, and the day-to-day operations. Supersedes the older mkcert/Caddy/mirrored-networking setup described in `MOBILE-ACCESS.md` and `KNOWN-ISSUES.md` (those remain as historical context).

## 1. Topology

- **Host OS:** Windows (LAN IP `192.168.1.100`, Ethernet) with WSL2.
- **WSL distro:** `Ubuntu-26.04`, user `vms`, project at `/home/vms/vms-livewire`.
  - Chosen to **isolate** this project from the other distro `Ubuntu` (24.04, user `chicks`). Nothing was installed or changed there.
  - Networking remains **NAT** (default) — **no `.wslconfig` change**, no mirrored mode, no `wsl --shutdown` requirement. Isolation was done per-project via Windows `portproxy`, not globally.
- **Reachable endpoints:**
  - `https://192.168.1.100:9443` — kiosk / browser (HTTPS, CA-signed cert).
  - `http://192.168.1.100:8888` — native mobile (RN) kiosk app / plain-HTTP API.
- **Windows forwarding layer** (done once, elevated PowerShell):
  - Firewall inbound allow: `VMS-HTTPS-9443`, `VMS-HTTP-8888` (TCP).
  - Portproxy:
    ```
    netsh interface portproxy add v4tov4 listenport=9443 listenaddress=0.0.0.0 connectport=9443 connectaddress=<wsl-nat-ip>
    netsh interface portproxy add v4tov4 listenport=8888 listenaddress=0.0.0.0 connectport=8888 connectaddress=<wsl-nat-ip>
    ```
  - WSL NAT IP today: `172.31.86.218` — **changes after every WSL shutdown/restart**. Re-point with `.certs/refresh-portproxy.ps1` (see §7).

## 3. TLS & certificates

- **Local CA** `VMS-Livewire Local CA` + site cert `CN=192.168.1.100` live in `.certs/` (gitignored): `ca.pem`, `ca-key.pem`, `192.168.1.100.pem`, `192.168.1.100-key.pem`.
- SANs: `IP:192.168.1.100, DNS:localhost, DNS:127.0.0.1`. Site key is EC P-256; cert valid 825 days.
- Generated by `.certs/make-certs.sh` (regenerate after a LAN-IP change).
- **Each kiosk/phone device must install `ca.pem`** for the browser to treat the site as secure — required for the kiosk camera (`getUserMedia` blocks non-secure contexts):
  - **Android:** Settings → Security → Install a certificate → CA certificate.
  - **iOS:** install the profile, then enable full trust (Settings → General → About → Certificate Trust Settings).

## 5. Kiosk API token

- Config: `config/kiosk.php` → `kiosk.token` = `env('KIOSK_API_TOKEN')`.
- Enforcement: `app/Http/Middleware/AuthenticateKiosk.php` (route group alias `kiosk` applied in `routes/api.php`); aborts 401 unless the `X-Kiosk-Token` header matches.
- **Rotate:** change `KIOSK_API_TOKEN` in `.env`, then restart the server (`bash start-server.sh`). Update the mobile app's stored token to match.
- During this deployment the token was **empty** (API answered anything with 200); a random 256-bit token was generated and written to `.env`.

## 6. Bugs found & fixed during deployment (root causes)

1. **HTTPS handshake fails — `ERR_SSL_PROTOCOL_ERROR` (browser), `SEC_E_INTERNAL_ERROR` (Windows schannel/curl.exe).**
   - **Cause:** the site was host-scoped (`https://192.168.1.100:9443`), so Caddy's TLS policy only matched ClientHellos **with SNI `192.168.1.100`**. Browsers and curl send **no SNI for bare-IP URLs** → Caddy aborted the handshake with TLS `internal_error` (alert 80). Loopback tests appeared to work because Caddy special-cases loopback connections.
   - **Not** HTTP/3, not the portproxy, not the cert chain, not schannel.
   - **Fix:** host-agnostic `https://:9443` → the `tls` directive becomes the default TLS policy for any/no SNI.
2. **HTTP 8888 serving empty `200` responses** (for any non-matching `Host` header, e.g. `127.0.0.1`).
   - **Cause:** same host-scoping class — site was `http://192.168.1.100:8888`, so other Host headers got Caddy's empty default instead of the app.
   - **Fix:** host-agnostic `http://:8888`.
3. **Kiosk API not actually enforced** — token was empty; now generated and verified (see §5).

## 7. Day-to-day operations

### Auto-start (in place)

On WSL boot, `cron @reboot` (user `vms`) runs `auto-start.sh`, which waits for MySQL on `127.0.0.1:3307` (up to 60 s), then runs `start-server.sh`. Log: `storage/logs/auto-start.log`. Manual run: `crontab -l` (installed entry), remove via `crontab -r`, stop it from starting with `crontab -e`.

> The Windows **portproxy** must still be refreshed after a `wsl --shutdown`/reboot (NAT IP changes) — see §7b.

### Start / restart services (in WSL)
```
wsl -d Ubuntu-26.04
cd /home/vms/vms-livewire
bash start-server.sh
```
MySQL starts via systemd (`serv mysql status`).

### 7b. Windows: portproxy refresh
`refresh-portproxy.ps1` auto-discovers the WSL NAT IP and re-adds firewall rules; run it elevated after a WSL restart (or register it as a scheduled task run at logon/logon-triggered WSL start).

### Stop
```
pkill -f 'frankenphp run'; pkill -f 'artisan queue:work'
```
(Use `pkill -f 'frankenphp ru[n]'` / `'artisan queue:wor[k]'` inside scripts so the pattern doesn't match the script's own shell.)

### After a WSL shutdown or reboot (NAT IP changes)
1. `wsl -d Ubuntu-26.04` → `bash ~/vms-livewire/start-server.sh`.
2. On Windows (elevated): `powershell -ExecutionPolicy Bypass -File \\wsl.localhost\Ubuntu-26.04\home\vms\vms-livewire\.certs\refresh-portproxy.ps1`.

### LAN IP changed
1. Regenerate certs: `wsl -d Ubuntu-26.04 bash /home/vms/vms-livewire/.certs/make-certs.sh` (edit `IP=` inside first).
2. Update `.env`: `APP_URL`, `VITE_HOST`.
3. Update `connectaddress` in `refresh-portproxy.ps1` (or current NAT IP) and re-run.
4. Re-add firewall rules if the port set changed.
